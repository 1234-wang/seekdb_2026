## Repeated work and implementation

For every document, BENG constructed a generic English analyzer, allocated its two pipeline objects, lowercased each word in a temporary normalizer arena, then allocated again and copied that word into caller-owned memory. BENG always disabled analyzer stopword and grouping stages; `ObAddWord` applies those policies after parsing.

The BENG parser now contains the existing whitespace tokenizer and basic English normalizer directly. It opens the same tokenizer on the same document and connects the same normalization stage, with no dynamic pipeline assembly. The new `get_next_owned` normalization entry point writes the normalized bytes directly into the parser caller's allocator. The parser can return those bytes without the temporary allocation and copy. This also eliminates the per-document scratch-arena allocation for normalizing BENG tokens.

The ordinary generic `get_next` interface retains its scratch-buffer semantics for other analyzer users. Delimiter classification, trimming, charset case conversion, token frequency, byte-length character counts, invalid-input checks, stopword/minimum-length policies and index/scoring formats are unchanged. Returned FTS tokens still remain valid after further reads, iterator reset/destruction and parser reinitialization, provided the caller keeps its allocator alive. Both implementations retain caller-owned storage until the enclosing operation releases it.

## Correctness and build

The same extended native test source passed all **8 tests** against the saved third-round libraries before the product change and against the rebuilt fourth-round libraries afterwards. The three new tests compare BENG with the generic two-stage analyzer, which continues using its original scratch-buffer interface.

Exact token bytes, lengths, frequencies, errors and iterator termination agree for **1,372 document/collation combinations**: mixed Unicode and case variants, punctuation, controls and embedded NUL, a word longer than 64 KiB, every byte value from 0 through 255 at token boundaries across the four supported collations, and deterministic generated byte sequences in UTF-8 and binary encodings. Tests retain every token after parser reset and reinitialization, and verify lifecycle errors. The other five native regressions retain collision, collation, stopword concurrency and actual BENG word-map checks.

The first reference attempt exposed an oracle mistake: malformed UTF-8 may yield a successful but empty generic normalization result, which the legacy BENG wrapper rejects with `OB_INVALID_ARGUMENT`. Before any production change, the oracle was corrected to include that existing wrapper validation; the input corpus and error behavior were preserved. The original failing result is retained locally. The initial candidate build also exposed a protected logging method on the embedded tokenizer; the parser's diagnostic fields were corrected before the successful full Release rebuild. No product source changed after that successful build and test run.

The fixed repository Release toolchain completed `./build.sh release --make -j24` with exit code zero. The source patch and identical test-source hashes, both XML result locations, build metadata and every timing observation are in the [JSON artifact](fts-performance-2026-round4.json).
